# Account types (the old S/L Type Table, outside loans)

One sentence per line. Keep this note current when the feature changes.

**Why it exists**: the old system keeps every kind of member ledger account in `sltype` (classes in `slclass`: 11 cash, 12 loans, 13 accounts receivable, 22 savings, 24 time deposits, 26 accounts payable, 29 miscellaneous liabilities, 31 share capital, 41 income) and the chart accounts each posts to in `glcontrol`; see `pics/sl types.png`.
The new application reads both when it posts, so they must be kept somewhere: loan types (class 12) already had Loan Setup, the other classes had no screen and could only be changed in the old system or in the database.
**Account Types** (`AccountTypeController`, `/api/admin/account-types`, **administrators only**; rules in the pure `AccountTypeRules`; screen `AccountTypesPage`, Settings > Products and the side menu, view `accounttypes`).
`GET` lists every class with its types, the number of accounts of each type where the class has an account table (`sd`, `td`, `sc`, `ar`, `ap`) and the number of ledger links.
`PUT /{class}/{code}` changes a type, `POST /{class}?copyFrom=` adds one as a copy of another type of the same class (the whole `sltype` row and its `glcontrol` links are copied, the code is the next free one), `GET /{class}/{code}/accounts` lists the ledger links and `PUT` on the same path points one link at another account.
**Only settings the application obeys are offered**, so nothing on the screen is a switch that does nothing: the name (20) and full name (30), the order in lists, in use or switched off, and per class: savings has the interest rate (the yearly rate of the interest run and of a new account), the minimum balance (what a withdrawal must leave), the **maximum balance** (`SLTypeMAXBAL`; a deposit that would take the balance over it is refused by `SavingsRules.checkDeposit`; empty is stored as the old system's 999,999,999.00, meaning no limit) and **dormant after (months)** (`SLTypeDORM_TERM`, unit 4 = months; see Savings dormancy below); time deposit has the minimum balance (the smallest placement); share capital the minimum balance (what a member must hold).
Share capital keeps its own maximum on each account (`SCMAX_BAL`), so the type's maximum is not offered there; the share capital dormancy fee (10.00 on Paid up Share Capital in the old data) is not applied by the new application and is not offered.
The other columns of `sltype` (passbook, tax flags and so on) are left exactly as they are and come along when a type is copied; add a field to `AccountTypeRules.fields` only when the application starts to obey it. The tax flag (`SLTypeISTAXFREE`) is 1 on every type in the data and the application does not read it.
**Rules**: a type and its code are never renumbered, and a type that was ever used is never deleted (accounts and posted entries point at it), only switched off; **a type nothing ever used can be deleted** (`DELETE /{class}/{code}?reason=`, with `GET /{class}/{code}/delete-check` first; button Delete type), for one added by mistake: it is refused while any account of it, account summary (`slmastersum`), ledger balance (`slsum`), posted entry (`transdt`, which stands for the 51-million-row `sldtl`, whose index does not start with the type), front-office entry, cheque, passbook, hold, hold setting, joint account record, other subsidiary record (`osl`), time deposit paying interest or rolling over into it, loan type deduction line, loan application deduction, loan application paying into it or branch rebate setting points at it (`AccountTypeRules.deleteProblems`), and loan and cash types are never deleted here; its ledger links go with it, and the whole row and its links are written to the audit log (`account.type.delete`), so it can be put back by hand; PostgreSQL `V024` (applied) and MySQL `V061` (written, not applied) grant DELETE on `sltype`; a name is used once in a class; a type that a branch setting pays rebates into cannot be switched off; a reason is required for every change and the audit log gets the changed fields before and after (`account.type.update`, `.disable`, `.enable`, `.create`, `.link.change`, `.link.add`, `.link.remove`, `cash.drawer.add`, `.delete`; entity `account_type`, id `<branch>/<class>/<code>`); saving the same values writes nothing.
**Ledger links**: a link can be pointed at a detail account that is in use and of the same kind (asset, liability, equity, revenue, expense) as the one it replaces. A link can be **added** for a posting the class uses (from the old `sle_type` table's class patterns; a balance link is per account status from `cts_type`, any other link is for all statuses, number 99); its balance side is copied from the same link of another type of the class, or set by the kind of the account. A link can be **removed** only while no entry was ever posted through it (`transdt` and `transfo` are counted) and never the type's last balance link.
**First type of an empty class** (`POST /{class}/first`): a class with no types (14, 25, 41 in this data) gets type 1 with its names and one balance link on the class's first account status; everything else starts at the table's defaults and its other links are added afterwards.
**Cash class (11)**: its types (cash on hand, cash in bank, cheques, ATM) are fixed and cannot be renamed or copied, but each link can be repointed, and `GET/POST /cash/drawers` lists the cashiers' (event 52) and tellers' (event 53) drawers with who holds each number and adds a drawer: the number (31 to 94) gets a link on every cash type that keeps drawers of that kind, to the account the other drawers of that type use. A person takes a drawer through their teller number in Users. Bank accounts are kept in the bank screens.
Entries already posted keep their account; moving a link does not move a balance (that is a journal).
**Read only here**: loan types (kept in Loan Setup, which has their terms, rates, COA Links and Deductions).
There is no second approver, as in Loan Setup and the chart of accounts: the control is the administrator role, the required reason and the audit log.
No migration was needed for this screen: the application's database user already had INSERT and UPDATE on `sltype` and full rights on `glcontrol` from the loan setup grants.

**Savings dormancy** (`SavingsDormancyController`, `/api/savings-dormancy`, rules in the pure `DormancyRules`; screen `SavingsDormancyPage`, Settings > Membership > Savings dormancy and the side menu, view `dormancy`).
`GET /review` (administrators) lists the active savings accounts of every type with a dormancy period whose member has not deposited or withdrawn for that long, longest quiet first, at most 500 at a time; savings interest (transaction type 53) and dividends (54) do not count as activity, an account never used counts from the day it was opened, and a reactivated account counts again from the day it was reactivated (read from the audit log). Nothing is marked by itself.
`POST /mark` (administrators, reason required) marks the chosen accounts dormant (status 15 to 16); each is checked again and one no longer due is skipped and named. `GET /dormant?q=` and `POST /reactivate` (administrators and Membership Officers, reason required) find dormant accounts by client number or name and make one active again (16 to 15). Each account is audited (`savings.dormant.mark`, `savings.dormant.reactivate`, entity `savings_account`, id `<branch>/<client>/<type>/<ref>`).
A dormant account already refuses deposits and withdrawals at the teller (`SavingsRules`). No dormancy fee is charged (the savings types carry none).
**Database**: `sd` was insert-only for the application (V015's statement trigger). PostgreSQL `V021__savings_dormancy_status.sql` (applied) replaces that trigger on `sd` only with a row trigger that lets the application change nothing but the status and its "updated by / at" stamps, and only from active to dormant or back; closing an account is not opened up. MySQL `V058` grants UPDATE on just those three columns (written, **not applied**).

**Loan type deductions** (`LoanDeductionSetupController`, `/api/admin/loan-setup/types/{code}/deductions`, administrators, rules in `LoanDeductionRules`; tab Deductions on a loan type in Loan Setup, `LoanDeductions.tsx`): the lines an application of the type starts with (`loansldeduc`). A line goes to one of the member's own accounts (savings, share capital, payables, miscellaneous liabilities; the type must be in use and have a balance link), to a charge of the loan (a posting the loan type has a COA Link for), or to a chart account that takes postings. Add, change (description, order 1 to 98, where it goes, leave it off the printed slip) and remove, each with a reason, audited as `loan.type.deduction.add|change|remove` with the line before and after.
The amount is typed by the clerk on the application, so a new line gets the old system's "ask for the amount" formula; an existing line keeps its formula (the old system still reads it). The net proceeds line always stays last and cannot be removed (only its wording changes); lines of a kind this screen does not set (paying off another loan, balancing entries) keep where they go. Applications already saved keep their own copy of the lines (`loandeduc`). PostgreSQL `V020__loan_deduction_setup.sql` (applied) and MySQL `V057` (written, not applied) add UPDATE and DELETE on `loansldeduc`.

Not built: the Loan Wizard Parameters part of the old window (not looked into), the Sales Transactions tab (the new point of sale replaces it), sub-accounts, a share capital dormancy run and fee.
Tested by `AccountTypeRulesTest`, `AccountTypeTest` (rolls back), `DormancyRulesTest`, `SavingsDormancyTest` (rolls back), `LoanDeductionRulesTest`, `LoanDeductionSetupTest` (rolls back), `SavingsRulesTest` (maximum balance), `AccountTypesPage.test.tsx`, `SavingsDormancyPage.test.tsx` and `LoanDeductions.test.tsx`.

## Suggested accounts for a ledger link (2026-11-22)

When an administrator chooses the chart account of a link (Add a link, Change, or the first type of a class), the dialog shows up to three suggestions as chips under the account field; why each is suggested shows on hover, and pressing one fills in the account. Nothing is saved by a suggestion, and the link is checked as before when saved.

`GET /api/admin/account-types/{cls}/link-suggestions?event=&number=&type=&name=` (`AccountTypeController.suggestions`, rules `LinkSuggestions`, pure): in order, the accounts the same posting and status of the class's other types go to (the most used first), this type's same posting for its other statuses, then detail accounts in use of the kind the posting needs (a balance: asset for cash, loans and receivables, liability for deposits, funds and payables, equity for share capital; interest income, fees and penalties revenue; accrued payables and withholding tax liabilities) whose names share words with the type's name (counted double), the class's name and the posting's name. At most five come back; the screen shows the first three the field accepts (a Change keeps to the same kind). Tested by `LinkSuggestionsTest`, `AccountTypeTest`, `AccountTypesPage.test.tsx`.
