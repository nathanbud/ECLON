# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Decisions and current state

- **Database**: the app is built on top of an existing legacy **MySQL 5.6.22** database (`localhost:3311`, schema `iaccsbsucmpc01`, ~368 tables, 100M+ rows), not the PostgreSQL the guide specifies. MySQL is the default; the same code also runs on PostgreSQL (see the PostgreSQL bullet below). A copy, `iaccs_sim`, exists on the same server. **`iaccsbsucmpc01` itself is a backup kept for testing, not the real live database** (the owner said so), so write features are built and tried directly against it; keep writes insert-only and audited anyway, since the real system will follow the same code.
- **Legacy tables are treated as read-only** and mapped with `@Immutable` JPA entities. Table and column names are mixed-case (`ClientIDBrCode`, `COADesc`), and most tables use composite keys starting with a branch code. Hibernate is set to `ddl-auto: none` and the standard naming strategy so names are kept as declared.
- **Flyway is not used yet**: its current MySQL support does not cover 5.6. Connector/J is pinned to 8.0.33 for the same reason.
- **Sign-in**: people come from the legacy `access` table (enabled users only). Legacy passwords (`access.AccessPassword`) use an encrypted format that cannot be verified, so each person gets a new password, stored as a bcrypt hash in `ecis_user_credential`. Full detail: `coop-platform/documentation/state/sign-in.md`. **Access changes while signed in**: the server re-reads a person's level, roles and flags on every request (HTTP Basic, no session), so an administrator's change applies on the person's next action and nobody signs out. The window keeps up by itself: `AccessWatcher` (mounted in `SessionGate`) asks `GET /api/me/access?since=<fingerprint>` (`MyAccessController`: level, roles, every setting of Settings > Users except who the person is (switches, limits, numbers, and choices, lists and dates such as assignment, department, offices, client types and access expiry, shown by name), and the per-transaction-type rights, in that screen's words; only the fingerprint comes back when nothing changed) every 15 s and when the window regains focus; on a change it refreshes `me` (menu, tiles, buttons), reloads what is on screen, and shows a notice at the top right (Your access was changed: who and when from the audit log, You can now / You can no longer / Changed; `accessChanges.ts`). A request refused with 401 while signed in (account switched off, password reset, temporary password run out) signs out with a reason that the sign-in screen shows once (`takeSignOutReason` in `api/http.ts`). **A switched-off account** is refused with `X-Auth-Reason: ACCOUNT_DISABLED`, but only when the password is right (`SecurityConfig.authProvider` checks the lock, then the password, then disabled and an expired temporary password; a wrong password or unknown name gets the usual answer, so a name alone reveals nothing); the sign-in screen then shows an "Account disabled" notice (`DisabledNotice`), at sign-in and once after being signed out mid-session (within about 15 s, through `AccessWatcher`). Tested by `DisabledAccountSignInTest`, `SignInPage.test.tsx`, `http.test.ts`. A failed check is warned about once in the console (a server older than the app answers "not found": restart it with `scripts/run-backend.ps1`). Tested by `MyAccessTest`, `accessChanges.test.ts`, `AccessWatcher.test.tsx`, `http.test.ts`.
- **Creating users** (Settings > Users > New user, `POST /api/admin/users`, `UserAccountController.create`, `UserCreateRules`, `NewUserDialog`): an `access` row plus a temporary password, optionally copying another user's permissions (`access` columns except identity and secrets, `access_trans`, roles); ADMIN/SUPERADMIN only by a super administrator; audited USER_CREATED; the Users page has a title-bar menu (`UsersMenu`, Alt+U: New user, Ctrl+N; Show in the list: all, enabled, disabled, administrators, Membership Officers, needs a password, locked out, with counts; Audit Log), and an Enabled switch per row (`setUserEnabled` in `api/users.ts`: reads the stored `AccessIsDisabled` from the profile, then saves it through `PATCH .../profile`, so the same rules, clash check and `UPDATE:AccessIsDisabled` audit row apply; switching off asks first; not on your own row; needs `COOP_EDIT_ENABLED=true`), tested by `UsersPage.test.tsx`; grants PostgreSQL `V032` applied, MySQL `V069` not. **Wording**: screens say member, not client (the old tables and code keep client); the server's messages and labels too, except text stored in the ledger or audit details. Full detail: `coop-platform/documentation/state/sign-in.md`.
- **Roles and approval**: `ROLE_ADMIN` comes from legacy level ADMIN/SUPERADMIN, `PERM_MEMBER_EDIT` from the legacy `AccessCanEditClient` flag, and `ROLE_MEMBERSHIP_OFFICER` from `ecis_user_role` (granted with `PUT /api/admin/users/{username}/roles/MEMBERSHIP_OFFICER`). **Granting Membership Officer also switches on every permission switch of the person's Member tab** (`UserAccountController.memberTabSwitches`, read from `UserProfileController.TABS` "client", except the preference `AccessIsClientIDDefaultPrompt`; amounts, member types and own member no. untouched), in the same transaction as the role, one `UPDATE:<column>` audit row each (reason "Switched on with the Membership Officer role"), under the account-setup rules (not your own account; an administrator's only by a super administrator); the reply lists what was switched on; taking the role away leaves the switches. Tested by `UserProfileEditTest`. Profile edits are maker-checker: a person with edit permission submits a change (`ecis_member_change`, status PENDING); a Membership Officer who is not the requester approves (the client row is then updated, with an audit row per field in `ecis_audit_log`) or rejects with a reason. Editing is off unless `COOP_EDIT_ENABLED=true`. **A Membership Officer's own profile edit is applied at once, with no second approval** (`ChangeRules.appliesDirectly`, `MemberChangeService.submit(..., isOfficer)`; setting `coop.edit.officer-direct`, on by default, set it to `false` to bring back the second-person rule): the change is stored as APPROVED with the officer as both maker and decider, the client row is updated in the same transaction, and the audit log gets one `UPDATE:<column>` row per field (reason says it was made directly, no second approval) plus one `CHANGE_APPLIED_DIRECTLY` row; `/api/capabilities` has `direct` so the screen says Save instead of Send for approval. Anyone without the role still goes through approval. - **Database user**: the app runs as the limited MySQL user `coop_app` (SELECT everywhere; UPDATE on `client`; INSERT on `ecis_audit_log`; INSERT/UPDATE on `ecis_member_change` and `ecis_user_credential`; INSERT/DELETE on `ecis_user_role`; column-level UPDATE on 119 non-secret columns of `access` and the 19 permission columns of `access_trans`, never the password or one-time-code columns). ## Planned system (from ECIS.pdf)

A cooperative management platform covering membership, share capital, savings, loans, teller/cash, accounting/GL, treasury, procurement, inventory, POS, fixed assets, CIC (credit information) reporting, documents, workflow, audit, notifications and BI.

**Stack**
- Desktop client: Tauri 2 + React + TypeScript + MUI, TanStack Query, React Hook Form + Zod, Zustand only where client state is needed.
- Backend: Java LTS + Spring Boot, Spring Security, Spring Data JPA/Hibernate, Flyway, MapStruct, Bean Validation, OpenAPI, JUnit + Testcontainers.
- Data and infrastructure: PostgreSQL as the system of record. Keycloak (auth), Redis, Kafka, Camunda (workflow), MinIO (documents), JasperReports. Prometheus, Grafana, Loki and OpenTelemetry for observability. Docker, with GitHub Actions for CI/CD and Trivy/OWASP for scanning.

**Architecture**: a modular monolith that can later split into microservices. The planned module boundaries are: organization, security, membership, share, savings, loan, cash, accounting, treasury, procurement, inventory, sales, fixedasset, document, workflow, cic, notification, audit, reporting. Keep modules decoupled so they can be extracted.

**Planned layout** (`coop-platform/`): `apps/desktop`, `apps/admin-web`, `backend/coop-core`, `infrastructure/{docker,postgres,keycloak,redis,kafka,minio}`, `database/{migrations,seed}`, `documentation`, `scripts`, `.github/workflows`. The dev environment should start with a single `docker compose up -d`. Git flow uses `main`, `develop`, `feature/*`, `release/*` and `hotfix/*`.

## Non-negotiable rules from the guide

These constrain any design or code you write:
- **Single source of truth**: one member master, one GL, one transaction history, one inventory ledger, one loan subledger.
- **Posted financial transactions are immutable.** Fix them with POSTED → REVERSAL → CORRECTED TRANSACTION, never by editing.
- **Double-entry**: every applicable transaction must produce balanced entries (total debits = total credits) before posting.
- **Maker-checker**: CREATE → REVIEW → APPROVE → POST.
- **Segregation of duties**: teller ≠ teller supervisor, loan processor ≠ loan approver, journal creator ≠ journal approver.
- **Audit trail** on every change: user, timestamp, action, entity, previous and new values, reference number, IP and device or session where applicable, approval info, and the reason for any correction or reversal.
- **Permissions** are dotted strings (e.g. `loan.application.approve`, `accounting.period.close`, `cic.submit`) mapped to roles managed in Keycloak.
- Security (authn/z, encryption, logging, backup, privacy) is designed into each module, not added later.
