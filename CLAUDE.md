# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Decisions and current state

- **Database**: the app is built on top of an existing legacy **MySQL 5.6.22** database (`localhost:3311`, schema `iaccsbsucmpc01`, ~368 tables, 100M+ rows), not the PostgreSQL the guide specifies. PostgreSQL migration is deferred. A copy, `iaccs_sim`, exists on the same server. **`iaccsbsucmpc01` itself is a backup kept for testing, not the real live database** (the owner said so), so write features are built and tried directly against it; keep writes insert-only and audited anyway, since the real system will follow the same code.
- **Legacy tables are treated as read-only** and mapped with `@Immutable` JPA entities. Table and column names are mixed-case (`ClientIDBrCode`, `COADesc`), and most tables use composite keys starting with a branch code. Hibernate is set to `ddl-auto: none` and the standard naming strategy so names are kept as declared.
- **Flyway is not used yet**: its current MySQL support does not cover 5.6. Connector/J is pinned to 8.0.33 for the same reason.
- **Sign-in**: people come from the legacy `access` table (enabled users only). Legacy passwords (`access.AccessPassword`) use an encrypted format that cannot be verified, so each person gets a new password, stored as a bcrypt hash in `ecis_user_credential`. An administrator sets it with `PUT /api/admin/users/{username}/password`. The env-configured `DEV_API_USER` remains only as a bootstrap administrator. Keycloak replaces all of this later.
- **Roles and approval**: `ROLE_ADMIN` comes from legacy level ADMIN/SUPERADMIN, `PERM_MEMBER_EDIT` from the legacy `AccessCanEditClient` flag, and `ROLE_MEMBERSHIP_OFFICER` from `ecis_user_role` (granted with `PUT /api/admin/users/{username}/roles/MEMBERSHIP_OFFICER`). Profile edits are maker-checker: a person with edit permission submits a change (`ecis_member_change`, status PENDING); a Membership Officer who is not the requester approves (the client row is then updated, with an audit row per field in `ecis_audit_log`) or rejects with a reason. Editing is off unless `COOP_EDIT_ENABLED=true`.
- **Database user**: the app runs as the limited MySQL user `coop_app` (SELECT everywhere; UPDATE on `client`; INSERT on `ecis_audit_log`; INSERT/UPDATE on `ecis_member_change` and `ecis_user_credential`; INSERT/DELETE on `ecis_user_role`; column-level UPDATE on 119 non-secret columns of `access` and the 19 permission columns of `access_trans`, never the password or one-time-code columns). User account setup can be edited by administrators from the Users screen (not their own account; changing an administrator or a level needs a SUPERADMIN), with an audit row per field. Its password is in `db.txt` as `app_password`. Root is for administration only. The MySQL server's `read_only` was switched OFF at runtime so the app can write; it reverts on a MySQL restart unless `my.ini` is changed. New tables are in `coop-platform/database/migrations` (V001 to V003), applied by hand with the `mysql` client.
- **Front office (teller) window**: posted transactions are read from `transsum` (header), `transdt` (entries; positive amount = debit, negative = credit), `transck` (cheques) and `denomsum`/`denomdtl` (cash), all read-only. New transactions are drafts in `ecis_fo_draft` (checked for real accounts and debits = credits, never posted). **Cash handover is posted** (the owner asked for posted, not draft, from now on): the head cashier (`AccessIsHeadCashier`, drawer type 52 number 37 in practice) takes cash from the vault (type 31) and gives it to tellers (type 32); tellers give it back; the head cashier returns the rest to the vault. A hand-off between people sits in `ecis_cash_handover` as PENDING until the receiver counts it; if the count agrees it is posted (INSERT only) to `transsum` (module 4), two `transdt` lines (SLC 11, SLT 1, event 50 vault no. 99 / 52 cashier / 53 teller, `DTCTS_NUM` = drawer number, accounts 10001/10002/10003, receiver as `DTAPPRVBY`), `gltrans` (credit negative, no balance columns) and `denomsum`/`denomdtl` (count by note and coin). Vault moves post at once. Control numbers are `MAX+1` per transfer type across years; `TR_DOCNO` is `*` plus 7 digits. The write grants come from `V006_cash_handover.sql`, which an administrator runs by hand (try it on a copy first). `V007_drawer_controls.sql` adds drawer cash limits (`ecis_drawer_limit`, set by the head cashier), end-of-day blind counts with the difference recorded (`ecis_drawer_close`; returning cash to the vault is blocked until hand-offs are settled and tellers who worked have counted, unless the head cashier gives a reason, which is audited), running drawer balances (`ecis_drawer_snapshot` = last year's closing figure, plus this year's entries; rebuilt in the background at start; the date column has no index so always narrow by `TR_YEAR`), supervisor overrides (`ecis_fo_override`, requester cannot approve their own) and a `request_key` that makes a repeated hand-off post only once. The window polls `GET /api/front-office/handover/pulse` every 5 s for live alerts (EventSource cannot send the Basic header). The screen locks after 10 idle minutes. `scripts/run-backend.ps1` rebuilds and restarts the backend. Cash receipts into share capital and savings, and savings withdrawals, are now posted (see the share capital and savings entries below). Other transaction types (loan and other receipts, vouchers, cheques) are still drafts: map a real posted example first, as for those, and do not add writes for them without it. A separate table `coopsystem_cash_transfer` and transaction 2026/4/32/33617 exist that this app did not create; leave them alone. What a person may do comes from `AccessCanAccessFrontOffice` and `access_trans` (find/new per transaction type).
- **PostgreSQL later**: the data will be migrated to PostgreSQL, so keep SQL portable. MySQL-only forms (`LAST_INSERT_ID`, `ON DUPLICATE KEY`, `INSERT IGNORE`, `GROUP_CONCAT`, `YEAR()`, `information_schema` with `DATABASE()`, `IFNULL`, `DATE_FORMAT` and so on) live only in `ph.coop.core.db.Db`, which has helpers for generated keys, upserts, table/column checks and privilege checks; `PortableSqlTest` fails if they appear anywhere else. `LIMIT`, `NOW()`, `CONCAT_WS`, `COALESCE` and `FOR UPDATE` are fine. Still MySQL-specific: the `V001`-`V010` migration scripts, the pinned MySQL dialect/driver, and mixed-case legacy names (PostgreSQL folds unquoted names to lowercase). The PostgreSQL branches in `Db` are untested. **The legacy data is already copied into PostgreSQL** (container `eclon-postgres`, port 5440, database `coop`, schema `legacy`; all 380 tables except the 154M-row hourly snapshot, counts checked against MySQL) with keys, indexes and foreign keys being added from `database/postgres/migrations` V006/V007 (finished 2026-10-21: 1,081 indexes and 560 foreign keys; the other 25 MySQL links point at non-unique columns and are listed as comments at the end of V007) (generated by `scripts/gen-legacy-indexes.py`); the loader is `scripts/load-legacy-to-postgres.py`; see `documentation/postgres-legacy-load.md` and the `load-legacy-postgres` skill. The running app still uses MySQL.

Posting a journal also writes a legacy General Journal (transsum module 1 type 1, transdt, gltrans) and needs creator, approver and poster to be enabled legacy users. Statements (`/api/financial-statements`) read `gltrans`; finished years are summed once into `ecis_gl_year_balance` (V009, built by an admin with `POST /balances/build`). The `ACCOUNTANT` role is granted like `MEMBERSHIP_OFFICER`. The desktop screen is Reports > Accounting. V006 to V014 are applied on this database.

Needs V011 (INSERT on `sldtl`), a drawer, a department and `access_trans` CAN_NEW for type 10. Refused for non-active accounts, balance over `SCMAX_BAL` (the old override flow is not wired in), and a repeat for the same client within 60 seconds unless confirmed. Receipt number: typed (up to 8 letters/digits) or `*` plus 7 digits (the real source of the old pre-printed numbers is still unknown). **Share withdrawals are encoded** (`POST /api/front-office/share-withdrawals`, Withdraw button on the Share Capital tab, `ShareWithdrawalController`): a back-office Cash Voucher (module 2, type 21, tag 2) debiting the share capital and crediting the member's vouchers-payable account, mapped in `documentation/share-withdrawal-posting-map.md`; approved and posted on Disburse by `LoanReleaseController` (three different people), tested by `ShareWithdrawalPostingTest`. Not built: cheque payments, subscriptions, certificates, paying the cash out of vouchers payable. New control numbers use `Db.nextControlNumber` (`ORDER BY ... LIMIT 1 FOR UPDATE`, PostgreSQL-safe), not `MAX() ... FOR UPDATE`.
- **Savings (phase 8, read-only so far)**: legacy savings is subsidiary ledger class 22: accounts in `sd` (types: SD - Regular, Associate, Kiddies, Kaya; rate in `SDINT_RATE`), holds in `hold` (reasons in `hold_code`: collateral, earmarked, lost passbook, garnished, maintaining balance, TD certificate), movements in `sldtl` event 11 (credits negative, balance = -SUM(AMT)). Typical transaction types on a savings account: Cash Receipt (10), Deposit Withdrawal (23), Interest (Savings) (53), Dividends (54), journals and Remittance Journals. `GET /api/members/{b}/{c}/savings` and `.../savings/{type}/{ref}` (history with running balance and holds; available = balance minus all holds, never below zero); Savings tab on the client profile. `SDSTATUS` 15 Active, 16 Dormant, 17 Closed are inferred from the data (no lookup table). The GL account comes from `glcontrol` (class 22, event 11, number = status): 2010101 for types 1 to 3, 2010106 for Kaya; accrued interest uses event 75 and 2011603. Time deposits (`td`, class 24) are not read yet. **Savings deposits and withdrawals are posted** (`POST /api/front-office/savings/deposits`, `/withdrawals/check`, `/withdrawals`; Deposit and Withdraw buttons on the Savings tab), written by `MemberLedgerPoster` exactly like the real Cash Receipt (module 3 type 10) and Deposit Withdrawal (module 2 type 23) mapped in `documentation/savings-posting-map.md`; share payments use the same writer. A withdrawal is refused over the balance or the available balance (after holds) and on dormant or closed accounts. A withdrawal that leaves the balance under the account minimum (`SDMIN_BAL`), or is over the cashier's `AccessDisbursementLimit`/`AccessMaxWithdrawal`, needs a supervisor approval: the cashier asks through `ecis_fo_override` (kinds `SAV_MIN_BALANCE`, `SAV_DISB_LIMIT`, text from `/withdrawals/check`), a different supervisor approves, and posting spends that approval once (`used_ref`, V012); each use is audited. The old system logged these in `actvtlog`; the app has no write access there, so the audit log is used instead. **Interest on deposits is mapped and the calculation reproduced, not posted** (`SavingsInterest`, `documentation/savings-interest-map.md`): quarterly A.D.B. (end-of-day balances summed over the quarter, interest = sum x type rate / 36,500, half up, nothing under a 500 A.D.B.), the rate is the loan type's `sltype` rate and not the account's; `SavingsInterestRealDataTest` matches 359 of 360 posted amounts exactly. **The quarterly interest run is built** (`SavingsInterestController`, `SavingsInterestRun`: preview, encode vouchers per type tag 2, approve by a second person, post by a third, refused if the quarter already has type 53 vouchers; accounts with a zero ending balance are skipped, accounts with 100,000 or more interest are held back; `SavingsInterestRunTest` passes, post step included (rerun 2026-10-21)). Not built: cheque deposits, dividend postings, holds, reactivating dormant accounts (dormant accounts are refused until it is known how the old system treats them), time deposits.

Banks: `bankcode` lists the bank accounts (`BCID`, name, account no., ledger account `BCCOAID`); the ledger side is class 11 type 2, events 61 (current) and 62 (savings), `DTCTS_NUM` = bank id; Bank Deposit and Bank Withdrawal are types 33 and 35 in module 5. Segregation: verifier and approver differ from the encoder, the approver from the verifier (read from the audit log), and the application's approver cannot approve its voucher. **Single-person exemption:** a system administrator can let one named person (never themselves) do every step alone, with a reason, audited (`SingleHandGrants`, `/api/admin/single-hand-loans`, table `ecis_single_hand`); Users screen has a "Loans alone" switch with a reason dialog. `V017_loan_workflow.sql` (table plus column UPDATE on `loanapp`) was applied by an administrator by hand; `LoanWorkflowTest` skips if MySQL is back in `read_only` (`SET GLOBAL read_only=OFF` as root). **Cancel** (`POST /api/loan-applications/{id}/cancel`, button in the panel): status 5 with the date and person in `APPRV_DATE`/`APPRVBY` like the old system, reason in the audit log, refused once the voucher is posted; a cancelled application's unposted voucher can no longer be approved or posted. **Disapprove (4) is built** (`POST /api/loan-applications/{id}/disapprove`, button in the panel): from New or Verified, by someone with the approve right who did not encode it, with date and person in `APPRV_DATE`/`APPRVBY` like the two real ones (2023, 2024) and the reason in the audit log. ## Planned system (from ECIS.pdf)

A cooperative management platform covering membership, share capital, savings, loans, teller/cash, accounting/GL, treasury, procurement, inventory, POS, fixed assets, CIC (credit information) reporting, documents, workflow, audit, notifications and BI.

**Stack**
- Desktop client: Tauri 2 + React + TypeScript + MUI, TanStack Query, React Hook Form + Zod, Zustand only where client state is needed.
- Backend: Java LTS + Spring Boot, Spring Security, Spring Data JPA/Hibernate, Flyway, MapStruct, Bean Validation, OpenAPI, JUnit + Testcontainers.
- Data and infrastructure: PostgreSQL as the system of record. Keycloak (auth), Redis, Kafka, Camunda (workflow), MinIO (documents), JasperReports. Prometheus, Grafana, Loki and OpenTelemetry for observability. Docker, with GitHub Actions for CI/CD and Trivy/OWASP for scanning.

**Architecture**: a modular monolith that can later split into microservices. The planned module boundaries are: organization, security, membership, share, savings, loan, cash, accounting, treasury, procurement, inventory, sales, fixedasset, document, workflow, cic, notification, audit, reporting. Keep modules decoupled so they can be extracted.

**Planned layout** (`coop-platform/`): `apps/desktop`, `apps/admin-web`, `backend/coop-core`, `infrastructure/{docker,postgres,keycloak,redis,kafka,minio}`, `database/{migrations,seed}`, `documentation`, `scripts`, `.github/workflows`. The dev environment should start with a single `docker compose up -d`. Git flow uses `main`, `develop`, `feature/*`, `release/*` and `hotfix/*`.

## Non-negotiable rules from the guide

These constrain any design or code you write:
- **Single source of truth**: one member master, one GL, one transaction history, one inventory ledger, one loan subledger.
- **Posted financial transactions are immutable.** Fix them with POSTED → REVERSAL → CORRECTED TRANSACTION, never by editing.
- **Double-entry**: every applicable transaction must produce balanced entries (total debits = total credits) before posting.
- **Maker-checker**: CREATE → REVIEW → APPROVE → POST.
- **Segregation of duties**: teller ≠ teller supervisor, loan processor ≠ loan approver, journal creator ≠ journal approver.
- **Audit trail** on every change: user, timestamp, action, entity, previous and new values, reference number, IP and device or session where applicable, approval info, and the reason for any correction or reversal.
- **Permissions** are dotted strings (e.g. `loan.application.approve`, `accounting.period.close`, `cic.submit`) mapped to roles managed in Keycloak.
- Security (authn/z, encryption, logging, backup, privacy) is designed into each module, not added later.
