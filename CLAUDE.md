# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Decisions and current state

- **Database**: the app is built on top of an existing legacy **MySQL 5.6.22** database (`localhost:3311`, schema `iaccsbsucmpc01`, ~368 tables, 100M+ rows), not the PostgreSQL the guide specifies. MySQL is the default; the same code also runs on PostgreSQL (see the PostgreSQL bullet below). A copy, `iaccs_sim`, exists on the same server. **`iaccsbsucmpc01` itself is a backup kept for testing, not the real live database** (the owner said so), so write features are built and tried directly against it; keep writes insert-only and audited anyway, since the real system will follow the same code.
- **Legacy tables are treated as read-only** and mapped with `@Immutable` JPA entities. Table and column names are mixed-case (`ClientIDBrCode`, `COADesc`), and most tables use composite keys starting with a branch code. Hibernate is set to `ddl-auto: none` and the standard naming strategy so names are kept as declared.
- **Flyway is not used yet**: its current MySQL support does not cover 5.6. Connector/J is pinned to 8.0.33 for the same reason.
- **Sign-in**: people come from the legacy `access` table (enabled users only). Legacy passwords (`access.AccessPassword`) use an encrypted format that cannot be verified, so each person gets a new password, stored as a bcrypt hash in `ecis_user_credential`. Full detail: `coop-platform/documentation/state/sign-in.md`.
- **Roles and approval**: `ROLE_ADMIN` comes from legacy level ADMIN/SUPERADMIN, `PERM_MEMBER_EDIT` from the legacy `AccessCanEditClient` flag, and `ROLE_MEMBERSHIP_OFFICER` from `ecis_user_role` (granted with `PUT /api/admin/users/{username}/roles/MEMBERSHIP_OFFICER`). Profile edits are maker-checker: a person with edit permission submits a change (`ecis_member_change`, status PENDING); a Membership Officer who is not the requester approves (the client row is then updated, with an audit row per field in `ecis_audit_log`) or rejects with a reason. Editing is off unless `COOP_EDIT_ENABLED=true`. **A Membership Officer's own profile edit is applied at once, with no second approval** (`ChangeRules.appliesDirectly`, `MemberChangeService.submit(..., isOfficer)`; setting `coop.edit.officer-direct`, on by default, set it to `false` to bring back the second-person rule): the change is stored as APPROVED with the officer as both maker and decider, the client row is updated in the same transaction, and the audit log gets one `UPDATE:<column>` row per field (reason says it was made directly, no second approval) plus one `CHANGE_APPLIED_DIRECTLY` row; `/api/capabilities` has `direct` so the screen says Save instead of Send for approval. Anyone without the role still goes through approval. Registering, closing and reactivating a member and beneficiary changes are not covered by this and still need a second officer. Tested by `ChangeRulesTest` and `OfficerDirectEditTest`. Administrators read the audit trail (`ecis_audit_log`) at `GET /api/admin/audit-log` (filters: person, record, action, date, text; newest first, read only) on the Audit Log tile (`AuditLogPage`), tested by `AuditLogControllerTest`.
- **Database user**: the app runs as the limited MySQL user `coop_app` (SELECT everywhere; UPDATE on `client`; INSERT on `ecis_audit_log`; INSERT/UPDATE on `ecis_member_change` and `ecis_user_credential`; INSERT/DELETE on `ecis_user_role`; column-level UPDATE on 119 non-secret columns of `access` and the 19 permission columns of `access_trans`, never the password or one-time-code columns). Full detail: `coop-platform/documentation/state/database-user.md`.
- **Front office (teller) window**: posted transactions are read from `transsum` (header), `transdt` (entries; positive amount = debit, negative = credit), `transck` (cheques) and `denomsum`/`denomdtl` (cash), all read-only. New transactions are drafts in `ecis_fo_draft` (checked for real accounts and debits = credits, never posted). Full detail: `coop-platform/documentation/state/front-office-teller-window.md`.
- **PostgreSQL (the default for running the app)**: since 2026-11-08 the app itself defaults to PostgreSQL (`spring.profiles.default: postgres` in `application.yml`), so `scripts/run-backend.ps1` and `mvn test` both use it; set `SPRING_PROFILES_ACTIVE=mysql` to use the old MySQL database instead. The backend test suite passed on PostgreSQL (546 tests; one date-dependent journal test was fixed); the signed-in browser tests have not been run on it. Docker Desktop must be open and `eclon-postgres` running. `SPRING_PROFILES_ACTIVE=postgres` runs the same code on PostgreSQL (container `eclon-postgres`, port 5440, database `coop`, everything in schema `legacy`, user `coop_app`). Keep SQL portable: MySQL-only forms (`LAST_INSERT_ID`, `ON DUPLICATE KEY`, `GROUP_CONCAT`, `YEAR()`, `IFNULL`, `DATE_FORMAT` and so on) live only in `ph.coop.core.db.Db`, and `PortableSqlTest` fails if they appear anywhere else; write `(CAST(? AS CHAR) IS NULL OR col = ?)` for an optional filter, give every read that needs an order an `ORDER BY`, and lock a row that sits behind an outer join on its own first. `scripts/setup-postgres-app.ps1` builds the app's tables, grants and fixes there from the live MySQL schema (rerun it after a new MySQL migration); posted ledgers stay insert-only through a `deny_update` trigger. Full detail and what is still open (full reload of the old tables at cutover, name-search index): `coop-platform/documentation/state/postgresql-later.md`.
- **Accounting (phase 6)**: journals (`/api/journals`, DRAFT to FOR_REVIEW to APPROVED to POSTED, reversal) and periods (`/api/accounting-periods`) use `ecis_journal*` / `ecis_accounting_period` (V001, V008, V010). Posting a journal also writes a legacy General Journal (transsum module 1 type 1, transdt, gltrans) and needs creator, approver and poster to be enabled legacy users. Statements (`/api/financial-statements`) read `gltrans`; finished years are summed once into `ecis_gl_year_balance` (V009, built by an admin with `POST /balances/build`). The `ACCOUNTANT` role is granted like `MEMBERSHIP_OFFICER`. The desktop screen is Reports > Accounting. V006 to V014 are applied on this database.

## Planned system (from ECIS.pdf)

A cooperative management platform covering membership, share capital, savings, loans, teller/cash, accounting/GL, treasury, procurement, inventory, POS, fixed assets, CIC (credit information) reporting, documents, workflow, audit, notifications and BI.

**Stack**
- Desktop client: Tauri 2 + React + TypeScript + MUI, TanStack Query, React Hook Form + Zod, Zustand only where client state is needed.
- Backend: Java LTS + Spring Boot, Spring Security, Spring Data JPA/Hibernate, Flyway, MapStruct, Bean Validation, OpenAPI, JUnit + Testcontainers.
- Data and infrastructure: PostgreSQL as the system of record. Keycloak (auth), Redis, Kafka, Camunda (workflow), MinIO (documents), JasperReports. Prometheus, Grafana, Loki and OpenTelemetry for observability. Docker, with GitHub Actions for CI/CD and Trivy/OWASP for scanning.

**Architecture**: a modular monolith that can later split into microservices. The planned module boundaries are: organization, security, membership, share, savings, loan, cash, accounting, treasury, procurement, inventory, sales, fixedasset, document, workflow, cic, notification, audit, reporting. Keep modules decoupled so they can be extracted.

**Planned layout** (`coop-platform/`): `apps/desktop`, `apps/admin-web`, `backend/coop-core`, `infrastructure/{docker,postgres,keycloak,redis,kafka,minio}`, `database/{migrations,seed}`, `documentation`, `scripts`, `.github/workflows`. The dev environment should start with a single `docker compose up -d`. Git flow uses `main`, `develop`, `feature/*`, `release/*` and `hotfix/*`.

## Non-negotiable rules from the guide

These constrain any design or code you write:
- **Single source of truth**: one member master, one GL, one transaction history, one inventory ledger, one loan subledger.
- **Posted financial transactions are immutable.** Fix them with POSTED → REVERSAL → CORRECTED TRANSACTION, never by editing.
- **Double-entry**: every applicable transaction must produce balanced entries (total debits = total credits) before posting.
- **Maker-checker**: CREATE → REVIEW → APPROVE → POST.
- **Segregation of duties**: teller ≠ teller supervisor, loan processor ≠ loan approver, journal creator ≠ journal approver.
- **Audit trail** on every change: user, timestamp, action, entity, previous and new values, reference number, IP and device or session where applicable, approval info, and the reason for any correction or reversal.
- **Permissions** are dotted strings (e.g. `loan.application.approve`, `accounting.period.close`, `cic.submit`) mapped to roles managed in Keycloak.
- Security (authn/z, encryption, logging, backup, privacy) is designed into each module, not added later.
