# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Decisions and current state

- **Database**: the app is built on top of an existing legacy **MySQL 5.6.22** database (`localhost:3311`, schema `iaccsbsucmpc01`, ~368 tables, 100M+ rows), not the PostgreSQL the guide specifies. PostgreSQL migration is deferred. A copy, `iaccs_sim`, exists on the same server. **`iaccsbsucmpc01` itself is a backup kept for testing, not the real live database** (the owner said so), so write features are built and tried directly against it; keep writes insert-only and audited anyway, since the real system will follow the same code.
- **Legacy tables are treated as read-only** and mapped with `@Immutable` JPA entities. Table and column names are mixed-case (`ClientIDBrCode`, `COADesc`), and most tables use composite keys starting with a branch code. Hibernate is set to `ddl-auto: none` and the standard naming strategy so names are kept as declared.
- **Flyway is not used yet**: its current MySQL support does not cover 5.6. Connector/J is pinned to 8.0.33 for the same reason.
- **Sign-in**: people come from the legacy `access` table (enabled users only). Legacy passwords (`access.AccessPassword`) use an encrypted format that cannot be verified, so each person gets a new password, stored as a bcrypt hash in `ecis_user_credential`. An administrator can only issue a **temporary** password (`PUT /api/admin/users/{username}/password` with `validityHours` 1, 4, 24 (default) or 72): the system generates it (12 characters, no look-alikes), the reply shows it once, it is stored only as a hash (`ecis_user_credential.must_change`, `expires_at`, `V023_temporary_passwords.sql`, applied), and the audit row never holds it. Nobody issues one for themselves and only a SUPERADMIN issues one for an administrator. Signing in with it works only until it expires (a 401 with `X-Auth-Reason: TEMPORARY_PASSWORD_EXPIRED`), and until the person replaces it (`POST /api/me/password`, min 8 characters with letters and numbers, not the username, not a common password) every other endpoint answers 403 `PASSWORD_CHANGE_REQUIRED` (`TemporaryPasswordGate` in `SecurityConfig`); the desktop shows `ChangePasswordScreen` instead of the app. Issuing a new one also ends any sign-in already open for that person. Tested by `TemporaryPasswordTest` and `TemporaryPasswordSignInTest`. **Sign-in lockout:** 5 wrong passwords for a name within 15 minutes lock it for 15 minutes (`LoginAttempts`, in memory so a restart clears it; unknown names are counted too; a locked name is refused even with the right password, 401 with `X-Auth-Reason: ACCOUNT_LOCKED` and `Retry-After`; audit rows `signin.locked` and `signin.unlocked`); administrators see and lift locks from the Users screen (`GET /api/admin/locked-users`, `POST /api/admin/users/{username}/unlock`); tested by `LoginLockTest`. The env-configured `DEV_API_USER` remains only as a bootstrap administrator. Keycloak replaces all of this later.
- **Roles and approval**: `ROLE_ADMIN` comes from legacy level ADMIN/SUPERADMIN, `PERM_MEMBER_EDIT` from the legacy `AccessCanEditClient` flag, and `ROLE_MEMBERSHIP_OFFICER` from `ecis_user_role` (granted with `PUT /api/admin/users/{username}/roles/MEMBERSHIP_OFFICER`). Profile edits are maker-checker: a person with edit permission submits a change (`ecis_member_change`, status PENDING); a Membership Officer who is not the requester approves (the client row is then updated, with an audit row per field in `ecis_audit_log`) or rejects with a reason. Editing is off unless `COOP_EDIT_ENABLED=true`. Administrators read the audit trail (`ecis_audit_log`) at `GET /api/admin/audit-log` (filters: person, record, action, date, text; newest first, read only) on the Audit Log tile (`AuditLogPage`), tested by `AuditLogControllerTest`.
- **Database user**: the app runs as the limited MySQL user `coop_app` (SELECT everywhere; UPDATE on `client`; INSERT on `ecis_audit_log`; INSERT/UPDATE on `ecis_member_change` and `ecis_user_credential`; INSERT/DELETE on `ecis_user_role`; column-level UPDATE on 119 non-secret columns of `access` and the 19 permission columns of `access_trans`, never the password or one-time-code columns). User account setup can be edited by administrators from the Users screen (not their own account; changing an administrator or a level needs a SUPERADMIN), with an audit row per field. Its password is in `db.txt` as `app_password`. Root is for administration only. The MySQL server's `read_only` was switched OFF at runtime so the app can write; it reverts on a MySQL restart unless `my.ini` is changed. New tables are in `coop-platform/database/migrations` (V001 to V003), applied by hand with the `mysql` client.
- **Front office (teller) window**: posted transactions are read from `transsum` (header), `transdt` (entries; positive amount = debit, negative = credit), `transck` (cheques) and `denomsum`/`denomdtl` (cash), all read-only. New transactions are drafts in `ecis_fo_draft` (checked for real accounts and debits = credits, never posted). **Cash handover is posted** (the owner asked for posted, not draft, from now on): the head cashier (`AccessIsHeadCashier`, drawer type 52 number 37 in practice) takes cash from the vault (type 31) and gives it to tellers (type 32); tellers give it back; the head cashier returns the rest to the vault. A hand-off between people sits in `ecis_cash_handover` as PENDING until the receiver counts it; if the count agrees it is posted (INSERT only) to `transsum` (module 4), two `transdt` lines (SLC 11, SLT 1, event 50 vault no. 99 / 52 cashier / 53 teller, `DTCTS_NUM` = drawer number, accounts 10001/10002/10003, receiver as `DTAPPRVBY`), `gltrans` (credit negative, no balance columns) and `denomsum`/`denomdtl` (count by note and coin). Vault moves post at once. Control numbers are `MAX+1` per transfer type across years; `TR_DOCNO` is `*` plus 7 digits. The write grants come from `V006_cash_handover.sql`, which an administrator runs by hand (try it on a copy first). `V007_drawer_controls.sql` adds drawer cash limits (`ecis_drawer_limit`, set by the head cashier), end-of-day blind counts with the difference recorded (`ecis_drawer_close`; returning cash to the vault is blocked until hand-offs are settled and tellers who worked have counted, unless the head cashier gives a reason, which is audited), running drawer balances (`ecis_drawer_snapshot` = last year's closing figure, plus this year's entries; rebuilt in the background at start; the date column has no index so always narrow by `TR_YEAR`), supervisor overrides (`ecis_fo_override`, requester cannot approve their own) and a `request_key` that makes a repeated hand-off post only once. The window polls `GET /api/front-office/handover/pulse` every 5 s for live alerts (EventSource cannot send the Basic header). The screen locks after 10 idle minutes. `scripts/run-backend.ps1` rebuilds and restarts the backend. Cash receipts into share capital and savings, and savings withdrawals, are now posted (see the share capital and savings entries below). Other transaction types (loan and other receipts, vouchers, cheques) are still drafts: map a real posted example first, as for those, and do not add writes for them without it. A separate table `coopsystem_cash_transfer` and transaction 2026/4/32/33617 exist that this app did not create; leave them alone. What a person may do comes from `AccessCanAccessFrontOffice` and `access_trans` (find/new per transaction type).
- **PostgreSQL later**: the data will be migrated to PostgreSQL, so keep SQL portable. MySQL-only forms (`LAST_INSERT_ID`, `ON DUPLICATE KEY`, `INSERT IGNORE`, `GROUP_CONCAT`, `YEAR()`, `information_schema` with `DATABASE()`, `IFNULL`, `DATE_FORMAT` and so on) live only in `ph.coop.core.db.Db`, which has helpers for generated keys, upserts, table/column checks and privilege checks; `PortableSqlTest` fails if they appear anywhere else. `LIMIT`, `NOW()`, `CONCAT_WS`, `COALESCE` and `FOR UPDATE` are fine. Still MySQL-specific: the `V001`-`V010` migration scripts, the pinned MySQL dialect/driver, and mixed-case legacy names (PostgreSQL folds unquoted names to lowercase). The PostgreSQL branches in `Db` are untested. **The legacy data is already copied into PostgreSQL** (container `eclon-postgres`, port 5440, database `coop`, schema `legacy`; all 380 tables except the 154M-row hourly snapshot, counts checked against MySQL) with keys, indexes and foreign keys being added from `database/postgres/migrations` V006/V007 (finished 2026-10-21: 1,081 indexes and 560 foreign keys; the other 25 MySQL links point at non-unique columns and are listed as comments at the end of V007; 556 of the 560 keys are validated, 4 have old orphan rows: jointacct, coa, coac, wkfcanalysis). `client.Height`, `Weight` and `BloodType` stay in MySQL only (V008 drops them in PostgreSQL, the loader skips them) (generated by `scripts/gen-legacy-indexes.py`); the loader is `scripts/load-legacy-to-postgres.py`; see `documentation/postgres-legacy-load.md` and the `load-legacy-postgres` skill. The running app still uses MySQL.
- **Accounting (phase 6)**: journals (`/api/journals`, DRAFT to FOR_REVIEW to APPROVED to POSTED, reversal) and periods (`/api/accounting-periods`) use `ecis_journal*` / `ecis_accounting_period` (V001, V008, V010). Posting a journal also writes a legacy General Journal (transsum module 1 type 1, transdt, gltrans) and needs creator, approver and poster to be enabled legacy users. Statements (`/api/financial-statements`) read `gltrans`; finished years are summed once into `ecis_gl_year_balance` (V009, built by an admin with `POST /balances/build`). The `ACCOUNTANT` role is granted like `MEMBERSHIP_OFFICER`. The desktop screen is Reports > Accounting. V006 to V014 are applied on this database.
- **Share capital (phase 7, read-only so far)**: legacy share capital is subsidiary ledger class 31: accounts in `sc` (type names in `sltype`: Paid up Share Cap, Dep for Cap Subs, preferred types), movements in `sldtl` (credits negative, no stored balance; balance = -SUM(AMT) per type and reference number), event 11. `GET /api/members/{b}/{c}/shares` and `.../shares/{type}/{ref}` (ledger history with running balance); the client profile has a Share Capital tab. `sc.SCSTATUS` 15 and 17 are shown as Active and Closed, inferred from the data (no legacy lookup table). **Share payments are posted** (`POST /api/front-office/share-payments`, the Post payment button on the Share Capital tab): a Cash Receipt (module 3, type 10) written exactly like the real one mapped in `documentation/share-payment-posting-map.md` (transsum, 2 transdt, 1 sldtl, 2 gltrans; never slsum, sc or denom*), dated today, cash into the poster's own drawer. Needs V011 (INSERT on `sldtl`), a drawer, a department and `access_trans` CAN_NEW for type 10. Refused for non-active accounts, balance over `SCMAX_BAL` (the old override flow is not wired in), and a repeat for the same client within 60 seconds unless confirmed. Receipt number: typed (up to 8 letters/digits) or `*` plus 7 digits (the real source of the old pre-printed numbers is still unknown). **Share withdrawals are encoded** (`POST /api/front-office/share-withdrawals`, Withdraw button on the Share Capital tab, `ShareWithdrawalController`): a back-office Cash Voucher (module 2, type 21, tag 2) debiting the share capital and crediting the member's vouchers-payable account, mapped in `documentation/share-withdrawal-posting-map.md`; approved and posted on Disburse by `LoanReleaseController` (three different people), tested by `ShareWithdrawalPostingTest`. **Paying the cash out of vouchers payable is built** (`VoucherPayoutController`, Cash Voucher payment module 2 type 24, the whole balance from the cashier's own drawer, posted at once; see the Cash and teller entry). Not built: cheque payments, subscriptions, certificates. New control numbers use `Db.nextControlNumber` (`ORDER BY ... LIMIT 1 FOR UPDATE`, PostgreSQL-safe), not `MAX() ... FOR UPDATE`.
- **Savings (phase 8, read-only so far)**: legacy savings is subsidiary ledger class 22: accounts in `sd` (types: SD - Regular, Associate, Kiddies, Kaya; rate in `SDINT_RATE`), holds in `hold` (reasons in `hold_code`: collateral, earmarked, lost passbook, garnished, maintaining balance, TD certificate), movements in `sldtl` event 11 (credits negative, balance = -SUM(AMT)). Typical transaction types on a savings account: Cash Receipt (10), Deposit Withdrawal (23), Interest (Savings) (53), Dividends (54), journals and Remittance Journals. `GET /api/members/{b}/{c}/savings` and `.../savings/{type}/{ref}` (history with running balance and holds; available = balance minus all holds, never below zero); Savings tab on the client profile. `SDSTATUS` 15 Active, 16 Dormant, 17 Closed are inferred from the data (no lookup table). The GL account comes from `glcontrol` (class 22, event 11, number = status): 2010101 for types 1 to 3, 2010106 for Kaya; accrued interest uses event 75 and 2011603. **Time deposits (`td`, class 24) are read only so far** (`TimeDepositController`, Time Deposits tab on the member profile, `documentation/time-deposit-map.md`): a certificate's money is ledger event 11 and year-end accrued interest event 71, and its master row is never closed when it is paid out, so status comes from the ledger; interest at maturity is shown as an estimate (rate x term days / 360; 72% of real rollovers credit that less a flat 10.00). **Placing a certificate is built** (`TimeDepositPlacementController`, a Cash Receipt with the certificate credited to its type account, a 25.00 fee to 442202 and new `slmastersum` and `td` rows; the cashier types the rate and a supervisor allows one outside what was used for the term, kind `TD_RATE`; needs `V027_time_deposit_placement.sql`, INSERT on `td`, and `V028_td_trigger_definer.sql`, which re-creates the old BEFORE INSERT trigger `update_td_certno` (it sets `TDCERT_NUM` = `TDREF_NO`) with a definer that exists, because its original definer `root@%` is not on this server; both applied by an administrator). **Payout and renewal of a matured Short Term certificate are built and always by hand** (`TimeDepositClosureController` encodes the old back-office Cash Voucher: certificate, accrued interest (event 71) and the rest of the term interest to 50105 debited, vouchers payable or a new certificate credited, with a 10.00 renewal fee to 442202; approved and posted on the Disburse tab by two other people; `TimeDepositClosureTest`). **Nobody and nothing rolls over by itself**: the Front Office **TD Maturities** tab (`TimeDepositMaturityController`, badge on the tab and on the Front Office tile) lists matured and soon-maturing certificates with Pay out and Renew buttons. **The interest accrual run is built** (`TimeDepositAccrualController`, module 8 type 52: Lock In every month end, Short Term every December 31, event 71 credited per certificate and 50105 debited per department; preview, encode, approve, post by three people, started by hand on the Front Office TD Accruals tab; `documentation/time-deposit-accrual-map.md`, `TimeDepositAccrualPostingTest`, `TimeDepositAccrualRealDataTest`). **Lock In payout and renewal at maturity are built** through the same controller (interest = balance x rate% for each unpaid year, the clerk picks the years; the monthly accrual is taken back and the difference goes to 50105, a credit when over-accrued; no renewal fee; a Lock In may be renewed into Short Term or Lock In; mapped in the Lock In section of `documentation/time-deposit-map.md`). **Pre-termination is built** (a running certificate, button Pre-terminate on the member's Time Deposits tab: the whole certificate debited and optionally part re-placed, a 100.00 charge for Short Term or 1%/5% of the principal for Lock In to 442201, Short Term interest at 1% for the days held, Lock In interest none unless typed, the accrual taken back; mapped in `documentation/time-deposit-map.md`, tested in `TimeDepositClosureTest`). **Lock In interest withdrawn on an anniversary is built** (button Withdraw interest on a running Lock In: a voucher that debits the accrual and 50105 and credits vouchers payable, the principal untouched, limited to a year of interest per anniversary passed less what was withdrawn). Not built: partial withdrawals of principal that keep a certificate running. **Savings deposits and withdrawals are posted** (`POST /api/front-office/savings/deposits`, `/withdrawals/check`, `/withdrawals`; Deposit and Withdraw buttons in the Front Office **Member Accounts** tab (`SavingsTellerPanel`, default export `MemberAccountsPanel`)), written by `MemberLedgerPoster` exactly like the real Cash Receipt (module 3 type 10) and Deposit Withdrawal (module 2 type 23) mapped in `documentation/savings-posting-map.md`; share payments use the same writer. A withdrawal is refused over the balance or the available balance (after holds) and on dormant or closed accounts. A withdrawal that leaves the balance under the account minimum (`SDMIN_BAL`), or is over the cashier's `AccessDisbursementLimit`/`AccessMaxWithdrawal`, needs a supervisor approval: the cashier asks through `ecis_fo_override` (kinds `SAV_MIN_BALANCE`, `SAV_DISB_LIMIT`, text from `/withdrawals/check`), a different supervisor approves, and posting spends that approval once (`used_ref`, V012); each use is audited. The old system logged these in `actvtlog`; the app has no write access there, so the audit log is used instead. **Interest on deposits is mapped and the calculation reproduced, not posted** (`SavingsInterest`, `documentation/savings-interest-map.md`): quarterly A.D.B. (end-of-day balances summed over the quarter, interest = sum x type rate / 36,500, half up, nothing under a 500 A.D.B.), the rate is the loan type's `sltype` rate and not the account's; `SavingsInterestRealDataTest` matches 359 of 360 posted amounts exactly. **The quarterly interest run is built** (`SavingsInterestController`, `SavingsInterestRun`: preview, encode vouchers per type tag 2, approve by a second person, post by a third, refused if the quarter already has type 53 vouchers; accounts with a zero ending balance are skipped, accounts with 100,000 or more interest are held back; `SavingsInterestRunTest` passes, post step included (rerun 2026-10-21)). **The annual dividend and patronage refund run is built** (`DividendRun`, `DividendController`, Front Office Dividends tab, module 6 type 54: 8% of the average of the 12 month-end share capital balances of the year before the cut-off plus 8.23% of the loan interest, service fees and event 24 charges paid that year, fitted to the cent for 99.9% of the real 2026 members; the rates and the mutual benefit and hospitalization amounts are typed by the accountant because the old rules for the insurance amounts are not known; the rest goes to savings or share capital; preview, encode, approve by a second person, post by a third, once a year; `documentation/dividend-map.md`, `DividendRunRulesTest`, `DividendRunRealDataTest`, `DividendRunTest`). Not built: cheque deposits, holds, reactivating dormant accounts (dormant accounts are refused until it is known how the old system treats them), time deposits.
- **Chart of accounts setup** (`ChartOfAccountsController`, `/api/accounting/chart`, administrators and accountants, `AccountsPage` = tile Back Office): add an account (detail or summary), rename it, move it under another summary account (only while it has no ledger entries) and switch it off; accounts and numbers are never deleted or changed. Numbering follows the old chart (first digit = type 1 to 6, number starts with its parent's, parent is an enabled summary account of the same type); new rows copy the pattern of the recent legacy ones (`COAacct_tag` D/S, `COAconso_acct` = own number for detail, `COAcanGLOnly`, user and time stamped). An account that `glcontrol`, `bankcode` or `branches` points at cannot be switched off. Journals now refuse summary and switched-off accounts. - **Settings tile** (`SettingsPage`): the dashboard's one home for administrator controls: Users, Audit Log, Loan Setup (with co-maker holds), Chart of Accounts (administrators and accountants), and the not-yet-built System and Backup. The tile opens for administrators and accountants; each card is checked again per role, and a screen opened from Settings returns to Settings. - **Cash and teller (phase 9)**: **Vouchers payable are paid out in cash** (`VoucherPayoutController`, `/api/front-office/voucher-payouts`, panel Pay out vouchers payable on Front Office > Disburse): the old Cash Voucher payment (module 2, type 24) is a payable debit plus the cashier's cash credit, the whole balance, written by one cashier and posted at once; refused when the cashier's drawer holds less (the app's own rule) and a payment over the cashier's limit needs a supervisor (kind `VOUCHER_DISB_LIMIT`); mapped in `documentation/voucher-payout-map.md`, tested by `VoucherPayoutTest`; not built: the mixed multi-account type 24 vouchers. cash drawers, hand-offs (cash transfer), limits, blind end-of-day counts with variance, and supervisor overrides already exist in the front office window. **Only `transdt` lines tagged `DTUPD_TAG` 1 or 5 are in the general ledger** (their sum equals `gltrans` exactly for the account checked; tag NULL and 2 lines are not posted). Banks: `bankcode` lists the bank accounts (`BCID`, name, account no., ledger account `BCCOAID`); the ledger side is class 11 type 2, events 61 (current) and 62 (savings), `DTCTS_NUM` = bank id; Bank Deposit and Bank Withdrawal are types 33 and 35 in module 5. The old system has no reconciliation data (`bankrecon_setup` empty, `DTISCLEARED` unused), so reconciliation is new: `ecis_bank_recon` and `ecis_bank_recon_item` (V013) hold a statement balance on a date plus the ledger entries still outstanding; book balance (from `gltrans`) minus outstanding must equal the statement balance, and a different person finalizes it (`/api/banks`, Accounting > Banks tab, ACCOUNTANT or ADMIN). Outstanding entries carry over to the next statement; legacy rows are never changed. **Bank deposits and withdrawals of vault cash are posted** (`BankCashController`, `/api/front-office/bank-cash`, Bank deposit panel on the Handover tab, head cashier only; vault 10001 event 50 against the bank ledger account from `glcontrol` class 11 type 2 event 61/62 with number = bank id; count in `denomsum`; mapped in `documentation/bank-cash-posting-map.md`, tested by `BankCashPostingTest`). **Deposits of vault cheques are built** (`cheques: true` on `/bank-cash/deposits`, 100111 sub-ledger type 3 event 51, no count; panel on the Handover tab). **Bank charges and interest need no new feature**: the old system books them only inside the accountant's month-end Bank Reconciliation General Journal (bank vs 440501 interest income or 50317 charges), which the app's journals already cover (mapped in `bank-cash-posting-map.md`). Not built: an explicit "open drawer" step.
- **Cheque receipts (built, grant pending)**: share payments, savings deposits and loan payments can be paid partly or wholly by cheque (`cheques` list on the three requests; `ChequeFields` on their dialogs; lists from `GET /api/front-office/cheque-setup`). `MemberLedgerPoster.postVoucher` writes what the old Cash Receipt wrote, mapped in `documentation/cheque-receipt-posting-map.md`: a debit per cheque on 100112/100113 (sub-ledger type 3), cash line, member credits marked `DTCOCI_TYPE` 2, cash paying the member lines first and cheques the rest as separate `sldtl` rows (`CLRG_DAYS` = kind days + 2), one `gltrans` credit per row, and `transck` rows (cash row first). **Every cash receipt of the old system has a `transck` cash row; this app's receipts now write it too.** Needs `V024_cheque_receipts.sql` (INSERT on `transck`, run by an administrator; until then cheques are refused and cash receipts skip the `transck` row); `ChequeReceiptPostingTest` skips until then. Cheque numbers are 15 digits, dates 180 days back to 30 ahead, the same bank and number twice needs a confirmation. **Clearing is built** (`ChequeClearingController`, head cashier, accountant or administrator marks received cheques cleared in `transck.CKISCLEARED`, a reason is needed when early, audited; needs `V026_cheque_clearing.sql`; the old rule for when cheques clear is not known, see the map). **Money paid in by a cheque that is not cleared is held back from a savings account's available balance** (`ChequeRules.unclearedSql`, counted with the holds in the account list and in the withdrawal check; the old rule is unknown, so this is the app's own choice and clearing the cheque releases it). Not built: the `sldtl.CLRG_DAYS` countdown, **Cheques can be handed between drawers together with the cash** (`cheques` on the handover request and acceptance, `cheque_amount` on `ecis_cash_handover`, `V025_cheque_handover.sql` run by an administrator; written as a second pair of lines on 100111/100112/100113, see `documentation/cheque-receipt-posting-map.md`; cheques never leave the vault except in a bank deposit), **Returned cheques are built for savings deposits** (`ChequeReturnController`, a General Journal debiting the member and crediting where the cheque is now; the poster plus a different approving supervisor via `ecis_fo_override` kind `CHEQUE_RETURN`; Returned cheque panel on the Handover tab; needs V026 for the cleared flag). Not built: returning cheques that paid loans or share capital, cheques on payments out.
- **Loans (phase 10, read-only so far)**: a loan is a row of `loan` (43k rows; type names in `sltype` class 12, purpose in `loanpurpose`, collateral in `collateraltype`, term unit in `term`, payment mode in `paymentmode`, amortization in `amortype`); its ledger is class 12 of `sldtl` where **event 11 is principal (release = debit, payments = credits, so outstanding = the plain sum)**, 23 interest paid, 31 service fee (deducted at release), and others for accrued interest and penalties; the repayment schedule is `amortsched` (580k rows: `DUEDATE`, `PRINDUE`, `INTDUE`, `PRINBAL` = balance after); co-makers are in `comaker`. Applications are `loanapp` (32k, statuses New, Verified, Approved, Disapproved, Cancelled, Deferred, RELEASED in `loanappstatus`). `GET /api/members/{b}/{c}/loans` (`?asOf=`, `?includePaid=`) and `.../loans/{type}/{ref}`; Loans tab on the client profile. Arrears are principal only: principal due by the date minus principal paid (released minus outstanding), and days late of the oldest unpaid instalment. **`LoanSTATUS` is 11 current, 12 past due, 13 in litigation, 14 restructured** (the number `glcontrol` keys the loan's GL account by). The old data stops on 2026-04-24, so tests measure arrears from that date. Not built: applications and approval, release, payments with interest/fee/penalty rules, restructuring, collection, provisioning. The release and the payment are mapped in `documentation/loan-posting-map.md`: a release is a back-office Cash Voucher (type 21; one debit for the loan, credits for the service fee, deductions and the net proceeds into a member vouchers-payable account); a payment is a Cash Receipt with interest-first split, interest = outstanding x rate x days since last payment / 365 (verified on two loans; 2024 payments used 360). **Loan cash payments are posted** (`POST /api/front-office/loan-payments` and `/check`; Pay button on the Loans tab) through `MemberLedgerPoster.postVoucher` (cash line plus a principal line, event 11 with the loan status as `DTCTS_NUM`, and an interest line, event 23, number 99; ledger rows get the next sequence over all events; the first use of an event on an account adds its `slsum` row, which needs V014). Interest is `LoanRules.interest` (365-day year, plain rounding: exact on 14 of 18 real payments, one cent off on the rest). **Penalties:** a loan late beyond its grace period carries a penalty, taken first (then interest, then principal) and posted as an event 41 line, number 99 (`LoanPaymentController`, `LoanRules.penalty`). The program only **suggests** the amount (penalty mode 4: unpaid scheduled principal plus interest of each due instalment x rate x days since its due date / 365; exact in 72% of simple cases and about 6% overall, see `documentation/loan-posting-map.md`); the cashier may type another figure, and any figure different from the suggestion (every figure when the loan's penalty mode is not 4) needs a supervisor's approval through `ecis_fo_override` (kind `LOAN_PENALTY`, spent once on posting, audit action `loan.payment.override.used`). Tested in `LoanPaymentPostingTest` and `LoanRulesTest`. ## Planned system (from ECIS.pdf)

A cooperative management platform covering membership, share capital, savings, loans, teller/cash, accounting/GL, treasury, procurement, inventory, POS, fixed assets, CIC (credit information) reporting, documents, workflow, audit, notifications and BI.

**Stack**
- Desktop client: Tauri 2 + React + TypeScript + MUI, TanStack Query, React Hook Form + Zod, Zustand only where client state is needed.
- Backend: Java LTS + Spring Boot, Spring Security, Spring Data JPA/Hibernate, Flyway, MapStruct, Bean Validation, OpenAPI, JUnit + Testcontainers.
- Data and infrastructure: PostgreSQL as the system of record. Keycloak (auth), Redis, Kafka, Camunda (workflow), MinIO (documents), JasperReports. Prometheus, Grafana, Loki and OpenTelemetry for observability. Docker, with GitHub Actions for CI/CD and Trivy/OWASP for scanning.

**Architecture**: a modular monolith that can later split into microservices. The planned module boundaries are: organization, security, membership, share, savings, loan, cash, accounting, treasury, procurement, inventory, sales, fixedasset, document, workflow, cic, notification, audit, reporting. Keep modules decoupled so they can be extracted.

**Planned layout** (`coop-platform/`): `apps/desktop`, `apps/admin-web`, `backend/coop-core`, `infrastructure/{docker,postgres,keycloak,redis,kafka,minio}`, `database/{migrations,seed}`, `documentation`, `scripts`, `.github/workflows`. The dev environment should start with a single `docker compose up -d`. Git flow uses `main`, `develop`, `feature/*`, `release/*` and `hotfix/*`.

## Non-negotiable rules from the guide

These constrain any design or code you write:
- **Single source of truth**: one member master, one GL, one transaction history, one inventory ledger, one loan subledger.
- **Posted financial transactions are immutable.** Fix them with POSTED → REVERSAL → CORRECTED TRANSACTION, never by editing.
- **Double-entry**: every applicable transaction must produce balanced entries (total debits = total credits) before posting.
- **Maker-checker**: CREATE → REVIEW → APPROVE → POST.
- **Segregation of duties**: teller ≠ teller supervisor, loan processor ≠ loan approver, journal creator ≠ journal approver.
- **Audit trail** on every change: user, timestamp, action, entity, previous and new values, reference number, IP and device or session where applicable, approval info, and the reason for any correction or reversal.
- **Permissions** are dotted strings (e.g. `loan.application.approve`, `accounting.period.close`, `cic.submit`) mapped to roles managed in Keycloak.
- Security (authn/z, encryption, logging, backup, privacy) is designed into each module, not added later.
